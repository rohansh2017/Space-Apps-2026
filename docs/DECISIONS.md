<a id="d1"></a>**D1 Frame kernel location.** The spec names `moon_de440_220930.tf`; NAIF moved it to `fk/satellites/a_old_versions/`. → Download from there. Same file, so the frame definition is the spec's.

<a id="d2"></a>**D2 No `/api` directory.** The spec's P0 lists `/build, /web, /api`, but the API is optional (only for points outside the precomputed regions) and the build brief's layout has none. → Not created until that requirement appears.

<a id="d3"></a>**D3 Python 3.12, numba < 0.62.** Spec says Python 3.11. The dev machine is an Intel Mac with uv's 3.12; current llvmlite has no wheel for it. → `requires-python >= 3.11`, numba pinned below 0.62. No science impact.

<a id="d4"></a>**D4 Skyfield PCK segment.** `moon_pa_de440_200625.bpc` holds two segments and Skyfield keeps only the last (2426–2650). → `ephem._kernels` picks the segment covering 2026–2035. Verified against Horizons (VALIDATION.md).

<a id="d5"></a>**D5 Contract details the spec leaves open.** Little-endian binaries; a region = one site's 21 × 21 grid, row-major, site at index 220; heightmap row 0 = north, height = offset + value × scale; added `elev_m` to points (the local frame needs elevation), `terrain` to sites, and `index` to points. Full list in CLAUDE.md.

<a id="d6"></a>**D6 Constraint ranges.** The spec gives defaults only. → min/max chosen in `constraints.schema.json`: duration 1–30 d, sun 0–30 d, dark 0–720 h, Earth visibility 0–100 %, Earth elevation 0–10°, slope 0–30°, slip 0–30 d (±), radius 0–5 km (the grid's reach). Editable placeholders.

<a id="d7"></a>**D7 Site coordinates.** NASA published only a map of the 2024 Artemis III regions. → Where PGDA product 78 has a site DEM, the site uses the centre of that DEM footprint, marked approximate, with that source recorded. Five regions without any sourced coordinate are held in `sites_src.json` under `pending` and are not in `sites.json`: Peak near Cabeus B, Mons Mouton Plateau, Mons Mouton (region), de Gerlache Rim 2, Slater Plain. The spec says Connecting Ridge comes "from the PGDA 78 README"; that README has no coordinates, so the Site01 footprint centre is used.

<a id="d8"></a>**D8 Spec PDF stays at the repo root** (the brief references it there), not under `docs/spec/`.

<a id="d9"></a>**D9 Raw DEMs in R2.** The team asked for both LOLA DEMs to be stored in Cloudflare; the spec only puts derived files in R2. → Planned under `raw/` in the data bucket. Blocked: R2 is not enabled on the account.

<a id="d10"></a>**D10 Exact curvature.** The spec says to subtract the curvature drop d²/(2R). → The mask uses exact spherical geometry (ray along a great circle, angle = atan2(r₁cosθ − r₀, r₁sinθ)), which is what d²/(2R) approximates; the two differ by about 0.01° at 300 km. Tested against a far ridge and a flat sphere.

<a id="d11"></a>**D11 Rays stop at the DEM edge.** The 80 m DEM covers ±304 km around the pole, so for sites far from the pole some rays end before 300 km (Nobile Rim 2 is 183 km out). Terrain north of 80°S is not in any spec dataset. Accepted as a screening-grade limit.

<a id="d12"></a>**D12 Heightmap axes.** Heightmaps are sampled in the site's local east/north axes (row 0 = north, col 0 = west), not stereographic x/y, so the 3D scene needs no rotation and azimuths line up with the engine.

<a id="d13"></a>**D13 Partial solar disk.** The horizon is taken as level across the 0.53° disk at the Sun's azimuth (circular-segment area). The spec does not define the shape; 1° bins make anything finer meaningless.

<a id="d14"></a>**D14 Frontend simplifications.** Panorama is plain Canvas 2D (no D3 needed yet). All ten ephemeris years (2.5 MB) load at start rather than per year; masks load per region on demand.

<a id="d15"></a>**D15 Ahead of plan.** `make data` already builds masks, slopes and heightmaps for all nine site grids (12 s), which the spec schedules for P2/P3, because it is the same code as one site.

<a id="d16"></a>**D16 Cloudflare/Gemini setup.** Cloudflare's agent setup installed the `cloudflare` Claude Code plugin (user scope). The optional `cf` CLI was not installed because the project uses Wrangler. Gemini is called over REST (Interactions API, model `gemini-4-hydrogen`), so the `@google/genai` SDK is not installed: the Worker needs one `fetch`.

<a id="d17"></a>**D17 Five Artemis III regions deferred.** Peak near Cabeus B, Mons Mouton Plateau, Mons Mouton, de Gerlache Rim 2 and Slater Plain have no published centre coordinate (NASA released a map image only; PGDA 78 and two literature searches gave nothing usable). → The list is final at 12 sites; these five stay under `pending` in `build/sites_src.json` rather than being guessed. To add one: put its lat/lon and source in `sites` there and run `make data`. Mons Mouton is still covered by the IM-2 landing site.

<a id="d18"></a>**D18 Gemini tooling.** The optional `gemini-api-dev` skill and Docs MCP server are not installed: the project's only Gemini use is two Worker routes over REST.

<a id="d19"></a>**D19 Finder searches forward only.** The spec says slip range ±30 days. A slipped launch cannot land earlier, and the demo showed every top result before the slipped date. → Team decision (2026-11-14): start dates run from the planned hour to planned + slip range. The schema default stays 30 days; the panel label reads "later by up to". The 60-day performance target is tested as a 60-day forward range.

<a id="d20"></a>**D20 Site map without MapLibre.** The spec lists MapLibre over a static hillshade. → Two plain canvases (polar cap, and the selected site's 10 km grid) drawn from static hillshade PNGs. Same function (see sites, click to pick), no extra dependency, no tiles.

<a id="d21"></a>**D21 New contract file: basemaps.** `basemap.json` plus 8-bit `basemaps/pole.png` (80 m DEM block-averaged to 800 m, relief x4) and `basemaps/{region}.png` (20 m DEM, ±5.25 km), in stereographic x/y axes. Hillshade lighting is fixed (upper left, 35 deg), not the real Sun, and the map caption says so. `tour.json` is now written from the hand-authored `build/tour_src.json` and is no longer synthetic.

<a id="d22"></a>**D22 Illustrative 3D detail.** The terrain is 20 m per cell, which renders as a smooth slab from 2 m eye height. → A procedural soil normal map and albedo, a random star field, a glare sprite on the Sun and a stylised Earth (correct phase and angular size, invented surface). None of it feeds any number, and the app footer says which parts are illustrative. Soil relief strength scales with solar elevation so contrast stays readable at grazing angles (display choice, like the exposure scaling).

<a id="d23"></a>**D23 Overlapping regions.** Shackleton rim and Peak near Shackleton grids overlap. → A custom coordinate that is within 500 m of a grid point of the selected site stays with that site; otherwise the nearest point of any region wins.

<a id="d24"></a>**D24 R2 with a bundled fallback.** The Worker answers `/data/*` from R2 and falls back to the copy bundled in the static assets, so a failed or stale upload cannot break the demo (the spec's "local build as the backup"). `raw/` keys are never served. Responses carry `x-data-source: r2|assets`.

<a id="d25"></a>**D25 PGDA comparison is a pattern check.** PGDA's map is an 18.6-year average at the surface of 60 or 120 m terrain; ours is 2026–2035 at 2 m above 20 m terrain. → Pass criterion is Pearson r ≥ 0.5 across each site's 441 points, with the means reported, not an equality test.

<a id="d26"></a>**D26 Nudge step is one grid point (500 m), not 100 m.** The spec's nudge moves the site 100 m, but horizon masks exist only at the 500 m grid, and a 100 m move needs a new ray-march (offline, numba). → The nudge moves to the neighbouring grid point closest to the chosen compass direction (`nudgeNeighbour`), labelled "500 m N/E/S/W", and ±1 day. The summary tiles show each metric's change since the last nudge. Upgrade path: precompute a finer grid around the demo sites.

<a id="d27"></a>**D27 Side-by-side as paired panoramas.** The spec allows split 3D or paired panoramas. → Paired panoramas with paired metric tiles and pass/fail chips, scrubbed together; the 3D view stays on the opened alternative. A second WebGL scene would halve the frame rate on the 30 fps target.

<a id="d28"></a>**D28 Tour mechanics.** Three steps from `tour.json` in a card above the 3D view, Explorer mode only. Step 1 adds a small inline sketch of an Earth sunrise against the polar Sun path (the spec's "contrasting with an Earth sunrise"); step 2 starts lunar-day playback; step 3 points at the nudge control. Switching to Planner closes it.

<a id="d29"></a>**D29 Mission room details.** One Durable Object per room id (`getByName`), WebSocket hibernation API, latest state kept in DO storage so late joiners catch up. The room message gains `point_index` (custom grid point, or null) beyond the spec's four fields, and the room also broadcasts `{type: "presence", count}` so the UI can show "2 connected" (the demo's proof that two browsers are in step). The DO checks message shape only; each browser validates incoming constraint values against `constraints.schema.json` and ignores unknown sites, points and out-of-range dates. Room ids are random `tb-xxxxxx` and carried in `?room=`; there is no auth, which is fine for a hackathon demo and is noted here. The browser never echoes a state it just received (`lastRoomKey`).

<a id="d30"></a>**D30 Room test needs the Worker.** Vite preview cannot host a Durable Object, so `room.spec.ts` is skipped unless `ROOM_TEST=1`; `make e2e-room` starts `wrangler dev` on port 8788 for it and `make check` includes it; `make e2e-live` runs it against the deployed Worker.

<a id="d31"></a>**D31 Gemini sentence entry.** Interactions API over REST from the Worker (`gemini-4-hydrogen`, the model the current docs use; one constant to change), `constraints.schema.json` read from the Worker's own static assets and sent as `response_format.schema` with `additionalProperties: false`. The prompt asks for stated fields only, so a sentence that names two constraints changes two fields. Limits: 300 characters, 10 requests per minute per client IP per isolate. The browser re-validates strictly (`parseSuggestion`: unknown fields and out-of-range values are listed as rejected, never coerced), shows the proposal labelled as generated, and changes nothing until "Apply to the panel"; the finder runs only when the user presses it. Probe results 2026-11-14: "survive 4 days of dark, talk to Earth half the time" → `{max_continuous_dark_hours: 96, min_earth_visible_pct: 50}`; an injection sentence → `{}`; 3–11 s latency. The local `make e2e` mocks the route; `make e2e-live` calls the real one.

<a id="d32"></a>**D32 `.env` key names changed.** The team renamed the Cloudflare entries (`CLOUDFLARE_ACCOUNT_API_TOKEN`, `Cloudflare_R2_*`). `web/scripts/wrangler.sh` now tries `CLOUDFLARE_ACCOUNT_API_TOKEN`, then the old `Cloudflare_Token_Value`. The file also has a stray space after one `=`, which breaks `source .env` but not the grep-based scripts; left for the owner to fix.

<a id="d33"></a>**D33 Illumination map window and colour.** F15 shows sunlit % per grid point over the current mission window from the planned landing hour (441 series, recomputed when the site, date or duration changes; a few ms). Cells are 500 m squares at 78% opacity over the LOLA hillshade, coloured with the same single-hue ramp as the scenario matrix (`src/ramp.ts`), so one magnitude reads the same in both views; the legend sits under the map. A ten-year average would need no date and match PGDA's map more closely, but the planner's question is this mission's window.

<a id="d34"></a>**D34 Slope check criteria.** `validate_slopes.py` compares our Uint8 slopes with the LOLA slope product sampled at the same points; pass is Pearson r ≥ 0.9 and mean absolute difference < 1° per site. Measured: r 0.994–0.999, mean abs diff 0.26–0.33°, max 2.2° (whole-degree rounding plus the gradient stencil). Slope screening itself has been in the finder since P2 (`max_slope_deg`).

<a id="d35"></a>**D35 Share link format.** `?site=&point=&t=&c=id:value,…&mode=`; constraints appear only when they differ from the schema defaults, so a default plan shares as `?site=…&t=…`. The address bar is updated with `replaceState` on every change (no history entries), and a Copy link button copies it. Values from a link go through the same validation as mission-room messages.

<a id="d36"></a>**D36 Horizon description mechanics.** The browser computes eleven facts from the engine (highest and lowest skyline sectors with elevations, sunlit % and max solar elevation over the mission window from the scrubber position, Sun/Earth state and hours to the next change) and always shows a template sentence built from them. "Describe with Gemini" sends only those facts to `/api/describe`; the reply is kept only if every number in it is one of the facts (rounded forms and day/hour conversions of the countdowns allowed), otherwise the template is shown with a note saying why. A generated sentence is dropped as soon as the facts change (new scrubber position, site or date). Same caps and secret handling as F21. First live run: with no direction facts the model answered that it "cannot say where the tracks meet the ridgeline", which has no numbers and so passed the number check; the facts now include the Sun's and Earth's current sectors and the sectors where each next meets the ridge, and a reply that reads as a refusal (`looksLikeDescription`) is replaced by the template too.

<a id="d37"></a>**D37 Real star field (built 2026-11-14).** The random star points are replaced by the Yale Bright Star Catalogue (BSC5, 9,110 entries: J2000 positions, V magnitude, B−V). CDS (VizieR V/50) was unreachable from the build machine, so the identical Harvard TDC copy is used. Stars are fixed in ICRF; a new contract file holds the ICRF→MOON_ME_DE440_ME421 rotation for every hour 2026–2035 as a Float32 quaternion (4 × 87,672 ≈ 1.4 MB), so the sky turns correctly with the Moon for any site and time. Aberration (≈ 20″) and proper motion over 26 years are ignored: far below a screen pixel. Point size follows magnitude; colour is an approximation from B−V via a black-body temperature, so star colours are approximate, not measured spectra. The table is checked by rotating Skyfield's apparent ICRF Sun direction and comparing it with the stored ephemeris vector.

<a id="d38"></a>**D38 5 m heightmaps where available (built 2026-11-14).** The spec's heightmaps are 256 × 256 from the 20 m DEM. Where a PGDA 78 5 m site DEM covers the whole 5 × 5 km patch, the heightmap is 1024 × 1024 (≈ 4.9 m per cell) from that file; otherwise it stays 256 × 256 from the 20 m DEM. Of our nine terrain sites, eight are covered (Shackleton rim via the Site07 file); IM-2 Mons Mouton is not. `sites.json` heightmaps gain `source` and `res_m`. Horizon masks, slopes and every number stay on the 20 m / 80 m DEMs, so no result or validation changes. The 5 m product is interpolated between LOLA tracks, so it is smoother than its pixel size suggests.

<a id="d39"></a>**D39 Procedural soil only where real relief is missing (built 2026-11-14; reversed by D43).** On 5 m patches the procedural crater and grain relief is dropped (real relief replaces it) and the ground is a uniform grey lit by the real Sun. It stays on 20 m patches and on the level ground used for points outside the patch, and the footer says where.

<a id="d40"></a>**D40 Terrain mesh and exposure for 5 m patches.** A uniform mesh over a 1024 px heightmap is about a million vertices: 60 fps on Apple GPUs, but it timed out the software-rendered browser tests and is a risk on weak laptop GPUs. → The mesh is 384 × 384 quads whose spacing grows away from the observer (≈ 3 m where you stand, ≈ 30 m at the patch edge), sampled bilinearly from the full heightmap and rebuilt when the observer moves; the heightmap file keeps all 5 m detail. Exposure: the old setting normalised flat ground and clipped every slope facing the Sun (the Shackleton rim falls 12° toward it). Now `0.6 / sin(Sun elevation + 3°)` puts flat ground at about 15–25% grey and lets the ACES tone curve roll sunward slopes off. Shadows are left physical: at 1° Sun elevation a 10 m rise shades about 570 m, so some sites are mostly dark at some hours, as they really are. Finding while checking: LOLA's 5 m surface is interpolated between laser tracks and many landing points sit on smooth slopes, so the 5 m ground looks smooth from 2 m eye height; small craters show where they exist.

<a id="d41"></a>**D41 Orientation test tolerance.** The parity test measures the angle between the rotated Sun and the stored Sun with `atan2(|a × b|, a · b)`. `acos` of the dot product turned the Float32 length error (≈ 1e-7) into a false 0.005° near zero; the real agreement is < 1e-4° (and < 1e-3° in azimuth and elevation through three site frames).

<a id="d42"></a>**D42 Load budget after P6.** The demo region now costs 9.2 MB of the 10 MB target (orientation table +1.4 MB at start, 5 m heightmap +1.8 MB per opened region). If the budget tightens, load orientation per year on demand (−1.3 MB) or ship 512 px heightmaps (10 m, −1.4 MB per region).

<a id="d43"></a>**D43 Soil texture back on 5 m patches (reverses part of D39, 2026-11-15).** With the procedural texture removed, the 5 m sites looked like smooth plastic: LOLA's 5 m surface holds nothing smaller than about 5 m and is smoothed between laser tracks, while real landing sites are textured by craters and rocks far below that size (team feedback with a screenshot). → The same procedural texture is used on every patch. Its largest bump or crater is about 1.5 m across (12 m tile, lattice period ≥ 1.5 m, crater radius ≤ 32 px of 512), so it only adds detail below what the 5 m data resolves and never invents a feature the data would show. Real orbital images (LROC NAC) were considered and not used: their shadows are fixed at capture time and would fight the moving Sun at grazing angles. Labelled illustrative in the footer and README.

<a id="d44"></a>**D44 Apollo sites removed from the app (team decision, 2026-11-15).** The spec lists Apollo 11, 15 and 17 in the curated site list for angle validation only. In the app they had no terrain, no 3D view and no finder, and read as unfinished. → Removed from `build/sites_src.json`; the app now lists the nine polar sites, all with terrain. They remain in `build/scripts/validate_horizons.py` with their own coordinates, so `make validate` and the Horizons result (0.0007°) are unchanged. The app's no-terrain code paths are kept (unused) in case a validation-only site returns.

<a id="d45"></a>**D45 Lit horizon ring from crest slopes (2026-11-15).** The distant ranges were a flat grey cut-out with fixed shading. → `make data` re-marches the site centre's 360 horizon rays (`crest_normals`, asserted to reproduce the mask) and stores, per azimuth, the unit normal of the DEM at the crest that forms the horizon, rotated into the site's east/north/up axes including the Moon's curvature (`ridges/{region}.bin`, 1,080 bytes). The scene lights each 1° of the ring with that normal and the real Sun direction, smoothed over ±2° (one gradient sample per crest is noisy), independent of whether the observer is lit, so distant peaks can glow while you stand in shadow. Not modelled: shadows cast onto the crests by other terrain, and the faces below the crest line (a 2° band fades into black). Grid points other than the centre use the centre's crests (they are 0–7 km apart; the ranges are mostly 10–300 km away). Rock texture on the ring is the illustrative soil texture.

<a id="d46"></a>**D46 Hardening pass (`/impeccable harden`, 2026-11-15).** Editing a constraint no longer deletes finder results: they stay, dimmed, under an "Out of date … Run again" banner (the user asked for this instead of a confirm dialog); changing the plan's site or date still clears them, since the results no longer describe that plan. Out-of-range constraint input keeps what was typed and shows an inline error naming the allowed range and the value the search still uses; the engine still only sees schema-valid values. A failed search, or a site whose terrain fails to load, is reported in place with a retry, and failed loads are not cached; only a failure of the initial data load replaces the app (with a Reload button). The scrubber and Play already worked from the keyboard (checked with a probe); the scrubber now speaks its date via `aria-valuetext`. One polite live region (`data-testid="announcer"`, no `role`, so the existing `role="status"` checks are unaffected) announces search start, finish and staleness. The long demo-path test is marked `test.slow()`: with five more tests it timed out at 30 s under parallel load, also on the previous commit without these changes.

<a id="d47"></a>**D47 Comparison wording (`/impeccable clarify`, 2026-11-15).** Result rows are titled by how they differ from the plan ("#1 · 5.0 km S · +16 days"), with the site and landing time below and the change in metrics once ("+97% sun, −158 h dark, +100% comms vs the plan"). The finder's difference text is split into parts (`diffParts`: where, when, a short signed shift, metrics) so titles, sentences and accessible names cannot disagree; `diffText` output is unchanged. The comparison view labels the alternative the same way. Every pass/fail chip shows its threshold ("✗ Dark ≤ 80 h"); results keep the constraint values they were searched with, so an out-of-date list shows the thresholds it was actually judged against. The HUD adds "Horizon toward Sun" and "Horizon toward Earth" (engine `maskAt` on the observer's own mask), so a low but positive solar elevation next to "Dark" explains itself. <a id="d67"></a>**D67 The Moon view in 3D: raised LOLA relief, the real Sun, terrain shadows (team request, 2026-11-15).** The team wanted to see cliffs and crater walls at the pole and site levels "like in real life"; the Moon view was a smooth sphere with fixed-light hillshade images on it. → New contract entry `basemap.json` `relief` (writer `build/scripts/build_relief.py`, `make data-relief`): 16-bit heights for the whole Moon (LDEM_16, 1024 × 512), the polar cap (20 m DEM averaged to 594 m, ±304 km) and ±32 km around each site (62.5 m), in the hillshades' own axes, 0.5 m steps, PNG filter Up (the web decoder now handles filters 0 and 2). In the browser they become RG8 textures (high and low byte; bilinear filtering is linear, so it filters the 16-bit value exactly; no mipmaps, which would round the high byte). One height function picks the finest loaded grid, blended over its edge (globe → pole → context → the site's own 5 m or 20 m heightmap). Three meshes are raised by it in the vertex shader: the 2° sphere, a 512 × 512 patch in stereographic x/y over the polar cap, and one over the flown-to site's ±32 km; each leaves the inside of the next finer one to it. The fragment shader lights the true (not exaggerated) slope with Lommel–Seeliger reflectance and the hour's Sun from the ephemeris, and marches the heights toward the Sun (40 steps growing geometrically to 200 km, curvature d²/2R subtracted) for the visible fraction of the 0.53° disk, the same disk model as the engine's masks. *Height* ×1–×5 (default ×3) changes only the geometry. Picking marches the ray between the highest and lowest the ground can be and bisects the first crossing (`moon.ts rayRelief`), so clicks and drags land where the drawn terrain is; grid dots, pins, badges and bearings sit on it; the camera stays above it and moves with its target when the slider changes. Decoration, named in *About the data* and the view's note: the exaggeration, one uniform ground brightness through an exposure curve 1 − exp(−3 × reflectance), and ground the Sun does not reach drawn at 14 % with the basemaps' fixed light so it keeps its shape. No number comes from the renderer: verdicts, angles and the HUD still come from the masks. Load: with the relief, `globe.png` (1.96 MB) and the context JPEGs (about 1.5 MB) are no longer fetched, so the first view and one fly-down went from 9.71 to 9.45 MB. Software renderers (the test machines) get 160 × 160 patches and a 6-step shadow march; the full suite timed out on them otherwise. Rejected: float textures (32-bit linear filtering is not universal in WebGL2; 16-bit half floats lose metres at polar heights); a shadow map (the Sun is a disk, not a point, and the march reuses the height function).

<a id="d74"></a>**D74 Moon view: the Sun's visibility baked once per hour, so the camera moves freely (team request, 2026-11-15).** After D71 the pole view looked right, but orbiting was choppy: 64–73 ms per frame (14–16 fps) on this machine's GPU (Intel Arc, Direct3D 11, 1200 × 1000). Every pixel ran the 40-step shadow march toward the Sun on every frame, although the Sun's visibility depends only on the terrain and the hour. Measured while dragging: the CPU was idle 82% of the time, the fragment shader cost about 50 ms, and merely compiling the march into the main shader cost that much even where it never ran (ANGLE on Direct3D; returning early, or dropping the march but keeping the rest, both came down to 8–17 ms). → The march moved out of the main shader into a bake pass (the same `relief()` and `sunVisible()`, shared GLSL). It renders the visibility into R8 textures: 2048² over the 75°S cap (about 445 m per texel), 1024² over a flown-to site's ±32 km context (62.5 m), 1024² over the 5 m site heightmap in its own east/north axes (about 5 m), and 4096 × 2048 equirectangular for the whole Moon. The main shader reads the finest target that covers the point. It re-bakes only when the hour, a relief grid or the flown-to site changes, never on a camera move or the Height slider (visibility uses true heights). While the hour runs (playback, scrubbing) it bakes half-size drafts, then the full size once the hour has rested 400 ms. `relief()` now reads its grids fine to coarse and stops once a finer grid fully covers the point (same blend, fewer texture reads). Results: orbiting 16–17 ms per frame (59–63 fps), Moon-view playback about 2× faster (88–92 → 46–53 ms per frame at 1600 × 900). Screenshots before and after (pole, Malapert Massif, close to its 5 m patch) differ by under 0.2 grey levels on average, with 0.1–0.25% of pixels (shadow edges) changing by more than 20. Software renderers (CI) bake at a quarter of each side, since they bake on the CPU. Adaptive pixel ratio while dragging was planned as a fallback and not needed. `GPU=1` now picks Direct3D 11 on Windows; its Metal-only flag had silently fallen back to software rendering there.
