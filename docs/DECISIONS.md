# Decisions

**D1 Frame kernel location.** The spec names `moon_de440_220930.tf`; NAIF moved it to `fk/satellites/a_old_versions/`. → Download from there. Same file, so the frame definition is the spec's.

**D2 No `/api` directory.** The spec's P0 lists `/build, /web, /api`, but the API is optional (only for points outside the precomputed regions) and the build brief's layout has none. → Not created until that requirement appears.

**D3 Python 3.12, numba < 0.62.** Spec says Python 3.11. The dev machine is an Intel Mac with uv's 3.12; current llvmlite has no wheel for it. → `requires-python >= 3.11`, numba pinned below 0.62. No science impact.

**D4 Skyfield PCK segment.** `moon_pa_de440_200625.bpc` holds two segments and Skyfield keeps only the last (2426–2650). → `ephem._kernels` picks the segment covering 2026–2035. Verified against Horizons (VALIDATION.md).

**D5 Contract details the spec leaves open.** Little-endian binaries; a region = one site's 21 × 21 grid, row-major, site at index 220; heightmap row 0 = north, height = offset + value × scale; added `elev_m` to points (the local frame needs elevation), `terrain` to sites, and `index` to points. Full list in CLAUDE.md.

**D6 Constraint ranges.** The spec gives defaults only. → min/max chosen in `constraints.schema.json`: duration 1–30 d, sun 0–30 d, dark 0–720 h, Earth visibility 0–100 %, Earth elevation 0–10°, slope 0–30°, slip 0–30 d (±), radius 0–5 km (the grid's reach). Editable placeholders.

**D7 Site coordinates.** NASA published only a map of the 2024 Artemis III regions. → Where PGDA product 78 has a site DEM, the site uses the centre of that DEM footprint, marked approximate, with that source recorded. Five regions without any sourced coordinate are held in `sites_src.json` under `pending` and are not in `sites.json`: Peak near Cabeus B, Mons Mouton Plateau, Mons Mouton (region), de Gerlache Rim 2, Slater Plain. The spec says Connecting Ridge comes "from the PGDA 78 README"; that README has no coordinates, so the Site01 footprint centre is used.

**D8 Spec PDF stays at the repo root** (the brief references it there), not under `docs/spec/`.

**D9 Raw DEMs in R2.** The team asked for both LOLA DEMs to be stored in Cloudflare; the spec only puts derived files in R2. → Planned under `raw/` in the data bucket. Blocked: R2 is not enabled on the account.

**D10 Exact curvature.** The spec says to subtract the curvature drop d²/(2R). → The mask uses exact spherical geometry (ray along a great circle, angle = atan2(r₁cosθ − r₀, r₁sinθ)), which is what d²/(2R) approximates; the two differ by about 0.01° at 300 km. Tested against a far ridge and a flat sphere.

**D11 Rays stop at the DEM edge.** The 80 m DEM covers ±304 km around the pole, so for sites far from the pole some rays end before 300 km (Nobile Rim 2 is 183 km out). Terrain north of 80°S is not in any spec dataset. Accepted as a screening-grade limit.

**D12 Heightmap axes.** Heightmaps are sampled in the site's local east/north axes (row 0 = north, col 0 = west), not stereographic x/y, so the 3D scene needs no rotation and azimuths line up with the engine.

**D13 Partial solar disk.** The horizon is taken as level across the 0.53° disk at the Sun's azimuth (circular-segment area). The spec does not define the shape; 1° bins make anything finer meaningless.

**D14 Frontend simplifications.** Panorama is plain Canvas 2D (no D3 needed yet). All ten ephemeris years (2.5 MB) load at start rather than per year; masks load per region on demand.

**D15 Ahead of plan.** `make data` already builds masks, slopes and heightmaps for all nine site grids (12 s), which the spec schedules for P2/P3, because it is the same code as one site.

**D16 Cloudflare/Gemini setup.** Cloudflare's agent setup installed the `cloudflare` Claude Code plugin (user scope). The optional `cf` CLI was not installed because the project uses Wrangler. Gemini is called over REST (Interactions API, model `gemini-4-hydrogen`), so the `@google/genai` SDK is not installed: the Worker needs one `fetch`.

**D17 Five Artemis III regions deferred.** Peak near Cabeus B, Mons Mouton Plateau, Mons Mouton, de Gerlache Rim 2 and Slater Plain have no published centre coordinate (NASA released a map image only; PGDA 78 and two literature searches gave nothing usable). → The list is final at 12 sites; these five stay under `pending` in `build/sites_src.json` rather than being guessed. To add one: put its lat/lon and source in `sites` there and run `make data`. Mons Mouton is still covered by the IM-2 landing site.

**D18 Gemini tooling.** The optional `gemini-api-dev` skill and Docs MCP server are not installed: the project's only Gemini use is two Worker routes over REST.

**D19 Finder searches forward only.** The spec says slip range ±30 days. A slipped launch cannot land earlier, and the demo showed every top result before the slipped date. → Team decision (2026-11-14): start dates run from the planned hour to planned + slip range. The schema default stays 30 days; the panel label reads "later by up to". The 60-day performance target is tested as a 60-day forward range.

**D20 Site map without MapLibre.** The spec lists MapLibre over a static hillshade. → Two plain canvases (polar cap, and the selected site's 10 km grid) drawn from static hillshade PNGs. Same function (see sites, click to pick), no extra dependency, no tiles.

**D21 New contract file: basemaps.** `basemap.json` plus 8-bit `basemaps/pole.png` (80 m DEM block-averaged to 800 m, relief x4) and `basemaps/{region}.png` (20 m DEM, ±5.25 km), in stereographic x/y axes. Hillshade lighting is fixed (upper left, 35 deg), not the real Sun, and the map caption says so. `tour.json` is now written from the hand-authored `build/tour_src.json` and is no longer synthetic.

**D22 Illustrative 3D detail.** The terrain is 20 m per cell, which renders as a smooth slab from 2 m eye height. → A procedural soil normal map and albedo, a random star field, a glare sprite on the Sun and a stylised Earth (correct phase and angular size, invented surface). None of it feeds any number, and the app footer says which parts are illustrative. Soil relief strength scales with solar elevation so contrast stays readable at grazing angles (display choice, like the exposure scaling).

**D23 Overlapping regions.** Shackleton rim and Peak near Shackleton grids overlap. → A custom coordinate that is within 500 m of a grid point of the selected site stays with that site; otherwise the nearest point of any region wins.

**D24 R2 with a bundled fallback.** The Worker answers `/data/*` from R2 and falls back to the copy bundled in the static assets, so a failed or stale upload cannot break the demo (the spec's "local build as the backup"). `raw/` keys are never served. Responses carry `x-data-source: r2|assets`.

**D25 PGDA comparison is a pattern check.** PGDA's map is an 18.6-year average at the surface of 60 or 120 m terrain; ours is 2026–2035 at 2 m above 20 m terrain. → Pass criterion is Pearson r ≥ 0.5 across each site's 441 points, with the means reported, not an equality test.

**D26 Nudge step is one grid point (500 m), not 100 m.** The spec's nudge moves the site 100 m, but horizon masks exist only at the 500 m grid, and a 100 m move needs a new ray-march (offline, numba). → The nudge moves to the neighbouring grid point closest to the chosen compass direction (`nudgeNeighbour`), labelled "500 m N/E/S/W", and ±1 day. The summary tiles show each metric's change since the last nudge. Upgrade path: precompute a finer grid around the demo sites.

**D27 Side-by-side as paired panoramas.** The spec allows split 3D or paired panoramas. → Paired panoramas with paired metric tiles and pass/fail chips, scrubbed together; the 3D view stays on the opened alternative. A second WebGL scene would halve the frame rate on the 30 fps target.

**D28 Tour mechanics.** Three steps from `tour.json` in a card above the 3D view, Explorer mode only. Step 1 adds a small inline sketch of an Earth sunrise against the polar Sun path (the spec's "contrasting with an Earth sunrise"); step 2 starts lunar-day playback; step 3 points at the nudge control. Switching to Planner closes it.

**D29 Mission room details.** One Durable Object per room id (`getByName`), WebSocket hibernation API, latest state kept in DO storage so late joiners catch up. The room message gains `point_index` (custom grid point, or null) beyond the spec's four fields, and the room also broadcasts `{type: "presence", count}` so the UI can show "2 connected" (the demo's proof that two browsers are in step). The DO checks message shape only; each browser validates incoming constraint values against `constraints.schema.json` and ignores unknown sites, points and out-of-range dates. Room ids are random `tb-xxxxxx` and carried in `?room=`; there is no auth, which is fine for a hackathon demo and is noted here. The browser never echoes a state it just received (`lastRoomKey`).

**D30 Room test needs the Worker.** Vite preview cannot host a Durable Object, so `room.spec.ts` is skipped unless `ROOM_TEST=1`; `make e2e-room` starts `wrangler dev` on port 8788 for it and `make check` includes it; `make e2e-live` runs it against the deployed Worker.

**D31 Gemini sentence entry.** Interactions API over REST from the Worker (`gemini-4-hydrogen`, the model the current docs use; one constant to change), `constraints.schema.json` read from the Worker's own static assets and sent as `response_format.schema` with `additionalProperties: false`. The prompt asks for stated fields only, so a sentence that names two constraints changes two fields. Limits: 300 characters, 10 requests per minute per client IP per isolate. The browser re-validates strictly (`parseSuggestion`: unknown fields and out-of-range values are listed as rejected, never coerced), shows the proposal labelled as generated, and changes nothing until "Apply to the panel"; the finder runs only when the user presses it. Probe results 2026-11-14: "survive 4 days of dark, talk to Earth half the time" → `{max_continuous_dark_hours: 96, min_earth_visible_pct: 50}`; an injection sentence → `{}`; 3–11 s latency. The local `make e2e` mocks the route; `make e2e-live` calls the real one.

**D32 `.env` key names changed.** The team renamed the Cloudflare entries (`CLOUDFLARE_ACCOUNT_API_TOKEN`, `Cloudflare_R2_*`). `web/scripts/wrangler.sh` now tries `CLOUDFLARE_ACCOUNT_API_TOKEN`, then the old `Cloudflare_Token_Value`. The file also has a stray space after one `=`, which breaks `source .env` but not the grep-based scripts; left for the owner to fix.

**D33 Illumination map window and colour.** F15 shows sunlit % per grid point over the current mission window from the planned landing hour (441 series, recomputed when the site, date or duration changes; a few ms). Cells are 500 m squares at 78% opacity over the LOLA hillshade, coloured with the same single-hue ramp as the scenario matrix (`src/ramp.ts`), so one magnitude reads the same in both views; the legend sits under the map. A ten-year average would need no date and match PGDA's map more closely, but the planner's question is this mission's window.

**D34 Slope check criteria.** `validate_slopes.py` compares our Uint8 slopes with the LOLA slope product sampled at the same points; pass is Pearson r ≥ 0.9 and mean absolute difference < 1° per site. Measured: r 0.994–0.999, mean abs diff 0.26–0.33°, max 2.2° (whole-degree rounding plus the gradient stencil). Slope screening itself has been in the finder since P2 (`max_slope_deg`).

**D35 Share link format.** `?site=&point=&t=&c=id:value,…&mode=`; constraints appear only when they differ from the schema defaults, so a default plan shares as `?site=…&t=…`. The address bar is updated with `replaceState` on every change (no history entries), and a Copy link button copies it. Values from a link go through the same validation as mission-room messages.

**D36 Horizon description mechanics.** The browser computes eleven facts from the engine (highest and lowest skyline sectors with elevations, sunlit % and max solar elevation over the mission window from the scrubber position, Sun/Earth state and hours to the next change) and always shows a template sentence built from them. "Describe with Gemini" sends only those facts to `/api/describe`; the reply is kept only if every number in it is one of the facts (rounded forms and day/hour conversions of the countdowns allowed), otherwise the template is shown with a note saying why. A generated sentence is dropped as soon as the facts change (new scrubber position, site or date). Same caps and secret handling as F21. First live run: with no direction facts the model answered that it "cannot say where the tracks meet the ridgeline", which has no numbers and so passed the number check; the facts now include the Sun's and Earth's current sectors and the sectors where each next meets the ridge, and a reply that reads as a refusal (`looksLikeDescription`) is replaced by the template too.

**D37 Real star field (built 2026-11-14).** The random star points are replaced by the Yale Bright Star Catalogue (BSC5, 9,110 entries: J2000 positions, V magnitude, B−V). CDS (VizieR V/50) was unreachable from the build machine, so the identical Harvard TDC copy is used. Stars are fixed in ICRF; a new contract file holds the ICRF→MOON_ME_DE440_ME421 rotation for every hour 2026–2035 as a Float32 quaternion (4 × 87,672 ≈ 1.4 MB), so the sky turns correctly with the Moon for any site and time. Aberration (≈ 20″) and proper motion over 26 years are ignored: far below a screen pixel. Point size follows magnitude; colour is an approximation from B−V via a black-body temperature, so star colours are approximate, not measured spectra. The table is checked by rotating Skyfield's apparent ICRF Sun direction and comparing it with the stored ephemeris vector.

**D38 5 m heightmaps where available (built 2026-11-14).** The spec's heightmaps are 256 × 256 from the 20 m DEM. Where a PGDA 78 5 m site DEM covers the whole 5 × 5 km patch, the heightmap is 1024 × 1024 (≈ 4.9 m per cell) from that file; otherwise it stays 256 × 256 from the 20 m DEM. Of our nine terrain sites, eight are covered (Shackleton rim via the Site07 file); IM-2 Mons Mouton is not. `sites.json` heightmaps gain `source` and `res_m`. Horizon masks, slopes and every number stay on the 20 m / 80 m DEMs, so no result or validation changes. The 5 m product is interpolated between LOLA tracks, so it is smoother than its pixel size suggests.

**D39 Procedural soil only where real relief is missing (built 2026-11-14; reversed by D43).** On 5 m patches the procedural crater and grain relief is dropped (real relief replaces it) and the ground is a uniform grey lit by the real Sun. It stays on 20 m patches and on the level ground used for points outside the patch, and the footer says where.

**D40 Terrain mesh and exposure for 5 m patches.** A uniform mesh over a 1024 px heightmap is about a million vertices: 60 fps on Apple GPUs, but it timed out the software-rendered browser tests and is a risk on weak laptop GPUs. → The mesh is 384 × 384 quads whose spacing grows away from the observer (≈ 3 m where you stand, ≈ 30 m at the patch edge), sampled bilinearly from the full heightmap and rebuilt when the observer moves; the heightmap file keeps all 5 m detail. Exposure: the old setting normalised flat ground and clipped every slope facing the Sun (the Shackleton rim falls 12° toward it). Now `0.6 / sin(Sun elevation + 3°)` puts flat ground at about 15–25% grey and lets the ACES tone curve roll sunward slopes off. Shadows are left physical: at 1° Sun elevation a 10 m rise shades about 570 m, so some sites are mostly dark at some hours, as they really are. Finding while checking: LOLA's 5 m surface is interpolated between laser tracks and many landing points sit on smooth slopes, so the 5 m ground looks smooth from 2 m eye height; small craters show where they exist.

**D41 Orientation test tolerance.** The parity test measures the angle between the rotated Sun and the stored Sun with `atan2(|a × b|, a · b)`. `acos` of the dot product turned the Float32 length error (≈ 1e-7) into a false 0.005° near zero; the real agreement is < 1e-4° (and < 1e-3° in azimuth and elevation through three site frames).

**D42 Load budget after P6.** The demo region now costs 9.2 MB of the 10 MB target (orientation table +1.4 MB at start, 5 m heightmap +1.8 MB per opened region). If the budget tightens, load orientation per year on demand (−1.3 MB) or ship 512 px heightmaps (10 m, −1.4 MB per region).

**D43 Soil texture back on 5 m patches (reverses part of D39, 2026-11-15).** With the procedural texture removed, the 5 m sites looked like smooth plastic: LOLA's 5 m surface holds nothing smaller than about 5 m and is smoothed between laser tracks, while real landing sites are textured by craters and rocks far below that size (team feedback with a screenshot). → The same procedural texture is used on every patch. Its largest bump or crater is about 1.5 m across (12 m tile, lattice period ≥ 1.5 m, crater radius ≤ 32 px of 512), so it only adds detail below what the 5 m data resolves and never invents a feature the data would show. Real orbital images (LROC NAC) were considered and not used: their shadows are fixed at capture time and would fight the moving Sun at grazing angles. Labelled illustrative in the footer and README.

**D44 Apollo sites removed from the app (team decision, 2026-11-15).** The spec lists Apollo 11, 15 and 17 in the curated site list for angle validation only. In the app they had no terrain, no 3D view and no finder, and read as unfinished. → Removed from `build/sites_src.json`; the app now lists the nine polar sites, all with terrain. They remain in `build/scripts/validate_horizons.py` with their own coordinates, so `make validate` and the Horizons result (0.0007°) are unchanged. The app's no-terrain code paths are kept (unused) in case a validation-only site returns.

**D45 Lit horizon ring from crest slopes (2026-11-15).** The distant ranges were a flat grey cut-out with fixed shading. → `make data` re-marches the site centre's 360 horizon rays (`crest_normals`, asserted to reproduce the mask) and stores, per azimuth, the unit normal of the DEM at the crest that forms the horizon, rotated into the site's east/north/up axes including the Moon's curvature (`ridges/{region}.bin`, 1,080 bytes). The scene lights each 1° of the ring with that normal and the real Sun direction, smoothed over ±2° (one gradient sample per crest is noisy), independent of whether the observer is lit, so distant peaks can glow while you stand in shadow. Not modelled: shadows cast onto the crests by other terrain, and the faces below the crest line (a 2° band fades into black). Grid points other than the centre use the centre's crests (they are 0–7 km apart; the ranges are mostly 10–300 km away). Rock texture on the ring is the illustrative soil texture.

**D46 Hardening pass (`/impeccable harden`, 2026-11-15).** Editing a constraint no longer deletes finder results: they stay, dimmed, under an "Out of date … Run again" banner (the user asked for this instead of a confirm dialog); changing the plan's site or date still clears them, since the results no longer describe that plan. Out-of-range constraint input keeps what was typed and shows an inline error naming the allowed range and the value the search still uses; the engine still only sees schema-valid values. A failed search, or a site whose terrain fails to load, is reported in place with a retry, and failed loads are not cached; only a failure of the initial data load replaces the app (with a Reload button). The scrubber and Play already worked from the keyboard (checked with a probe); the scrubber now speaks its date via `aria-valuetext`. One polite live region (`data-testid="announcer"`, no `role`, so the existing `role="status"` checks are unaffected) announces search start, finish and staleness. The long demo-path test is marked `test.slow()`: with five more tests it timed out at 30 s under parallel load, also on the previous commit without these changes.

**D47 Comparison wording (`/impeccable clarify`, 2026-11-15).** Result rows are titled by how they differ from the plan ("#1 · 5.0 km S · +16 days"), with the site and landing time below and the change in metrics once ("+97% sun, −158 h dark, +100% comms vs the plan"). The finder's difference text is split into parts (`diffParts`: where, when, a short signed shift, metrics) so titles, sentences and accessible names cannot disagree; `diffText` output is unchanged. The comparison view labels the alternative the same way. Every pass/fail chip shows its threshold ("✗ Dark ≤ 80 h"); results keep the constraint values they were searched with, so an out-of-date list shows the thresholds it was actually judged against. The HUD adds "Horizon toward Sun" and "Horizon toward Earth" (engine `maskAt` on the observer's own mask), so a low but positive solar elevation next to "Dark" explains itself. The Shackleton rim blurb now states the fact in the spec instead of "Demo story": the August 2026 launch was called off with no new date announced (Space.com); no new claims were added to other blurbs.

**D48 Shadow display fill (`/impeccable delight`, 2026-11-15).** In shadow the 3D view was black (correct physics, but the demo's slipped-date frame showed nothing). → A faint directional fill from straight overhead (intensity 0.3) and a small lift on the horizon ring's unlit parts (0.05), both scaled by the hidden share of the solar disk so a sunset fades instead of snapping. Overhead keeps the ground's relief readable; it is not earthshine (Earth is below the horizon on the slipped date). It is a display aid: tagged in the view while the Sun is more than half hidden ("In shadow · view brightened so the terrain stays visible"), named in the footer, and it feeds no number. The ring lift was tried at 0.09 and reduced to 0.05 because it flattened the real lit-versus-shaded contrast of the distant ranges. The finder's ranking is unchanged.

**D49 Full-screen, comparison-first layout (`/impeccable shape` + `layout`, 2026-11-15).** The challenge asks for rapid comparison of scenarios and a full-screen mode; the page was a scrolling column with one alternative at a time. → The 3D view fills the window between a top bar and a bottom band; the Plan panel (site, date, coordinates, constraints) is a collapsible left column with *Find alternatives* pinned to its foot, so it never scrolls away. The band holds the scrubber, nudges, the signature panorama and the *Compare* tray: the plan plus up to three pinned scenarios (`TRAY_MAX`), each computed by the engine like the plan and scrubbed together. It replaces the two-column side-by-side view (`Compare.tsx` removed). Opening a result pins it when there is room; a full tray asks which pin to replace. Pins are written into the share link (`pins=region:index@hour,…`) so a copied link reopens the same comparison. Map, scenario matrix and mission room moved into non-modal drawers (rail buttons; the room is a header button) that take focus, close on Escape and return focus. Focus moves to the results after a search and to the view's status line after *Open in 3D* or *View in 3D*. The footer is one line (screening grade and non-goals) plus *About the data*, a dialog with the sources and the full list of what the 3D view invents. *Full screen* uses the Fullscreen API and is hidden where the browser lacks it. Visual world "polar light": deep-shadow ground, regolith-grey panels, Public Sans (bundled via @fontsource; it has no ≤ ≥ ✓ ✗, so chips use words and icons), gold only for sunlight (Sun track, sunlit ramp, power fill), blue only for Earth, red/green only for pass/fail with icons and words; the matrix uses one ramp per metric. Defaults taken without a user answer: pins in the link, tray replaces side-by-side, Public Sans. Phones get their own pass next (`/impeccable adapt`).

**D50 Compare tray as a table, compare mode, adopt a pin (`/impeccable critique`, 2026-11-15).** The critique (25/40, against the comparison objective) found three P1s: the tray did not fit a 1280×720 full screen (82 px of internal scroll), its rows did not line up across columns, and a comparison could not end in a decision. → (1) While anything is pinned the band is in compare mode: the tray's heading joins the timeline strip, the tray spans the band, and the nudge row, the large skyline and the horizon description fold into a *Nudge, skyline and horizon description* disclosure (the plan's own skyline is in its tray column). The band may then take up to 62% of the height, so on a 720p projector the tray fits without scrolling and the 3D view keeps about 195 px; on 1440×900 it keeps 420 px. Tray skylines are drawn 44 px tall on windows under 800 px. (2) The tray is a table: a label column and one column per scenario share ten grid rows (CSS subgrid), so each metric reads straight across; each value keeps its own visually hidden label for screen readers. The best value in each row is bold, with "(best in the tray)" for screen readers; nothing is marked when every column ties. (3) *Make this the plan* on a pinned column makes that scenario the plan (point and date) and pins the old plan in its place; results are cleared because they described the old plan, and focus moves to the view. Unpin became an icon button in the column's title row. Kept as they were (choice left to us): the matrix stays a drawer.

**D51 Collapsible panels, resizable band, cinematic full screen (team request, 2026-11-15).** The countdown HUD collapses to its two countdowns, the plan/alternative card to its title, and the bottom band to the scrubber line (chevron buttons with `aria-expanded`). The band resizes from its top edge (a `role="separator"` grip: drag, arrow keys in 24 px steps, double-click resets to its natural height; limits 96 px to the window minus 212 px). A full tray's replace prompt reopens a collapsed band. *Full screen* is semi-cinematic: the view runs edge to edge under translucent chrome with a soft letterbox gradient; the Plan panel, HUD details, card details and band fold away; after 2.5 s without pointer movement or a key the header and rail fade out, the scrubber dims and the cursor hides; keyboard focus keeps the chrome visible; leaving full screen restores the layout the user had. The one-line screening-grade footer stays visible throughout (spec requirement). Transitions are off under `prefers-reduced-motion`.

**D52 Band tab and interface motion (team request, 2026-11-15).** The band's open/close control moved out of the scrubber row to one tab centred on its top edge, in the same place whether the band is open (down arrow, drops it) or closed (up arrow, raises it); the edge itself stays the resize grip. Motion is short and eased out (`cubic-bezier(0.22, 1, 0.36, 1)`, 160–260 ms) and only shows where something went: panel opens and closes (band, HUD, plan card, Plan panel, the full-screen fold and restore) morph with the View Transitions API, instant where the browser lacks it; drawers slide in from their edge; results, tray columns, prompts and the tour rise into place (results staggered 30 ms); buttons depress slightly while pressed; pinning pops the pin icon. Everything is reduced to near zero under `prefers-reduced-motion`. During a panel transition (~220 ms) the 3D view is a still frame.

**D53 Glitch-free panel transitions, one left panel at a time, minimizable alternatives, Latin-only font (team request, 2026-11-15).** Filmed at 1/20 speed (CDP `Animation.setPlaybackRate`): closing the Plan panel left a smeared blurred box, because `backdrop-filter` does not survive a View Transitions snapshot, and boxes that changed size stretched their text while morphing; overlays that moved (the in-view tags) cross-faded in two places at once. → Panels drop the blur for a near-opaque fill (`--panel` 93%; the blur was barely visible at 86%); size-changing groups (status card, HUD, alternatives, band) clip their content (`object-fit: none` anchored at their fixed corner) instead of scaling it; the in-view tags and the tour get their own transition names so they slide. Plan, Map and Scenario matrix share the left edge and are exclusive: opening one closes the others, and all slide out toward the rail the same way (the Plan rail button is always shown and toggles); the Mission room drawer is unaffected. The alternatives panel has a minimize button that folds it into its top-right corner as an "Alternatives 10" chip (focus moves to the chip; restoring focuses the list heading); a new search reopens it, and only a fresh search plays the list's entrance. The bundled font is now the Latin subset only (Public Sans' Latin range covers every character the UI uses, including ° · − ×): 18 font files became 6 and the app bundle went from 1.49 to 1.38 MB. `make perf` now also measures an empty page in the same browser, so a frame-rate ceiling set by the machine (30 fps on battery at 4%, also on the empty page; 60 fps for both on mains power) is not mistaken for an app regression. Because the Map drawer now closes the Plan panel, the snap note (invariant 9: snapped point and distance) is shown inside the Map drawer too; `make check` caught this.
