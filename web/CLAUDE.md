# web/ conventions

- React + TypeScript (strict) + Vite. Lint with `npm run lint` (oxlint), typecheck with `tsc -b`.
- `public/data/` holds generated contract files only. Never hand-edit them, except
  `constraints.schema.json`, which is authored there and is the single schema source.
- `src/engine/engine.ts` (P1+) is pure: no DOM, no React, no globals. HUD numbers come from it.
- No runtime network calls except the optional Gemini routes and the mission room.
- Deploy: `make deploy` from the repo root (uploads data to R2 with `scripts/upload-data.sh`, then `wrangler deploy`).
- `Scene3D.tsx` and `SiteMap.tsx` are memoised; pass them stable props so playback does not redraw them needlessly.
- `GPU=1 npx playwright test` runs Chromium on the real GPU (Metal on macOS, Direct3D 11 on Windows; used by `make perf`); the default is software rendering.
- `worker/room.js` is the mission room Durable Object (`MissionRoom`, binding `ROOM`, SQLite migration `v1`). It relays state and computes nothing. `src/room.ts` is the client; `App.tsx` applies incoming state after validating it.
- `/data/*`, `/room/*` and `/api/*` are in `run_worker_first`: anything else is served as a static asset and never reaches the Worker.
- `worker/copilot.js` (`POST /api/copilot`, F21/F26/F29: the one *Ask Gemini* button, D70; grounded extraction shared from `worker/gemini.js`), `worker/describe.js` (`POST /api/describe`, F22) and `worker/whynot.js` (`POST /api/whynot`, F27) call Gemini through `worker/gemini-call.js` (rate limit; model, thinking level and a 429/503 fallback model from the `vars` in `wrangler.jsonc`, D64; a 1024-token runaway cap: thinking counts against it, so never set it tight) with the `GEMINI_API_KEY` secret; the browser validates every reply (`src/gemini.ts`, `src/describe.ts`, `src/copilot.ts`, `src/whynot.ts`) and has a fallback.
- Gemini tokens are limited (D63): one small call per user press, nothing automatic, templates first. e2e mocks every `/api/*` Gemini route; only `gemini.spec.ts` under `make e2e-live` spends tokens.
- 3D: `src/starfield.ts` draws BSC5 stars rotated per hour by `engine.skyMatrix`; the horizon ring is lit from `ridges/{region}.bin` crest normals; `src/regolith.ts` is the illustrative sub-1.5 m soil and ring texture. Anything invented must be named in the footer's *About the data* dialog (`App.tsx`).
- Layout (D49): full-window grid in `index.css` (top bar, left rail, Plan side panel, the view's overlays, bottom band, one-line footer). Map, scenario matrix and mission room open in `Drawer`s; the compare tray (`Tray.tsx`) holds the plan plus up to `TRAY_MAX` pinned `ScenarioRef`s, which go in the share link as `pins`. Colours: gold only for sunlight, blue only for Earth, red/green only for pass/fail with words or icons.
- Moon view (D58): `MoonView.tsx` is the default stage; it and `Scene3D` replace each other (one WebGL context). `moon.ts` holds its pure geometry (MOON_ME ↔ three.js `(x, z, −y)`, trig-free stereographic, ray → grid, `gridStats`). Its bar is portalled into `.over` so no card covers it. Pins read one mask row per site via `loadSitePoint` (HTTP Range). Shader layers (D60, D62): `globe.png` → `pole.png` → per-site 20 m context map (on fly-down) → region map → the site heightmap shaded in the browser (only within about 8 km). Relief (D67, D71): with `basemap.relief`, four meshes (the sphere at 1° facets, a 512² patch over the 75°S cap, a 512² polar patch, a 512² patch around the flown-to site; 2° and 160² on software renderers) are raised in the vertex shader by the layered heights (globe → 75°S cap → pole → context → site heightmap, RG8 textures without mipmaps) × the Height slider (×1 by default), lit by the hour's real Sun with a shadow march toward it (40 steps, 6 on software renderers) baked into visibility textures once per hour, never per frame (D74: cap, context, site and whole-Moon targets; half-size drafts while the hour runs; the march must stay out of the main shader, which ANGLE on Direct3D slows even where it never runs), and `globe.png` and the context JPEGs are not fetched. Picking (`moon.ts rayRelief`) and every marker follow the raised ground; numbers never come from it. Topo (D68) is a shader overlay; its legend's numbers come from `basemap.json` and `reliefAt`. Stars (D61): BSC5 turned by the hour's orientation (`icrfToThree`), drawn first without depth so the Moon covers them; stars and the orientation load a year at a time (`Dataset.loadSky(hour)`). The Map drawer is gone (D61): map clicks and the F15 heat map live in the Moon view.
- Quick tour (F28, D65): steps are data in `src/onboarding.ts` (target = a `data-tour` attribute, `done` = a predicate over a small App snapshot); `Coach.tsx` rings the real control and advances when the predicate turns true. Keep it to about 30 s: one-click actions, one sentence each. A new target needs a `data-tour` attribute on a control that is always mounted while its step is shown. It never opens itself under `navigator.webdriver`; e2e opens it with `?tour=1`.
- Tray (D59): every column is a frozen `ScenarioRef`; *Pin this view* toggles the scenario in view; no live plan column (old `pins=plan` links become a snapshot on load).
- Accessibility conventions: one polite live region (`data-testid="announcer"`) for status messages, deliberately without `role` (tests count `role="status"`); result buttons carry `aria-label`s that start with their visible text; inline errors use `aria-describedby`/`aria-invalid`; failures are reported in place with a retry, never by replacing the whole app.
